<!--
  This file documents the staging-entry schema. It is itself a valid
  entry and is exercised by the schema validator's smoke check.

  Schema reference
  ----------------

  Every entry is a YAML-style front-matter block bracketed by two
  `---` fences. Three fields are REQUIRED — `uuid`, `timestamp`, and
  `proposed-text` (the lesson itself). The other three (`target`,
  `scope`, `rationale`) are OPTIONAL advisory hints: accepted but not
  validated at filing time, so a hand-filed lesson needs only its body.
  The fields:

    uuid           RFC 4122 v4 UUID. Generated by the emission site,
                   not the curator. Used as the filename prefix for
                   the pending temp file and as the de-dup key across
                   curation passes — a lesson already folded into the
                   evidence ledger is skipped if a restored snapshot
                   re-presents it.

    timestamp      ISO 8601 in UTC (`YYYY-MM-DDTHH:MM:SSZ`). Set to
                   the moment of capture, not the moment of curation.

    target         OPTIONAL advisory hint at the destination file, as
                   `<repo>/<path-from-repo-root>.md`. NOT validated at
                   filing time — captured targets were mostly wrong
                   (agents invented plausible paths nothing reads), so
                   the filing validator ignores its shape entirely. Omit
                   it for a quick hand-filed lesson; the curator clusters
                   by theme and picks the real destination itself.

                   The shape contract still lives in
                   `target_shape_valid` (`scripts/lib/staging-schema.sh`)
                   and is enforced by the curator's edit-path guard
                   against the destination the curator ACTUALLY PICKS at
                   promote time — not against whatever the lesson
                   suggested. The shapes that guard accepts:
                     a project repo with a checkout under ~/src:
                       <repo>/AGENTS.md
                       <repo>/CLAUDE.md
                       <repo>/.claude/<path>.md
                     flux (the context repo — additional shapes
                     because its sources of truth live outside .claude/):
                       flux/AGENTS.md
                       flux/CLAUDE.md
                       flux/.claude/<path>.md
                       flux/agents/<name>.md
                       flux/skills/<skill>/SKILL.md
                       flux/model-profiles.toml
                   A change to a project repo lands on a `lessons/*`
                   branch and through a PR, titled `[LESSONS] <summary>`,
                   which the user merges. A change to Flux commits
                   straight to `main`, as every Flux change does. Read the
                   diff before either lands: a repo-root AGENTS.md or
                   CLAUDE.md, an `agents/<name>.md`, a `skills/*/SKILL.md`
                   or `model-profiles.toml` loads into every session in
                   its scope, so its blast radius is global.

    scope          OPTIONAL advisory hint at the patch verb — `add`,
                   `modify`, or `remove`. Not enum-checked at filing.
                   `add` appends a new rule; `modify` changes an existing
                   one (curator quotes the replaced text in the PR body);
                   `remove` deletes an obsolete rule. The curator decides
                   the real verb when it drafts the change.

    rationale      OPTIONAL one-sentence justification — "why is this
                   worth recording?", usually the failure mode it
                   prevents. Fold it into the lesson prose if you like; a
                   separate field is not required.

    proposed-text  REQUIRED block scalar (note the trailing `|`) — the
                   lesson itself. For a hand-filed lesson this is just the
                   insight in evergreen prose; for an automated emission
                   site it is the exact text to insert / replace in the
                   destination file. Indent every body line by two
                   spaces. Body MUST NOT contain advice that weakens the
                   verification discipline — the drain hook applies
                   a case-insensitive, word-boundary blocklist (see
                   scripts/lib/staging-schema.sh for the current pattern
                   list) and rejects entries that hit it.

  How this file is used
  ---------------------

  - Emission-site skills copy the front-matter block as a starting
    point, fill in the required fields (plus any advisory hints they
    genuinely have), and write the result to
    `learnings/pending/<session-id>-<uuid>.md` via an atomic
    `pending/<file>.md.tmp` → `pending/<file>.md` rename.

  - The `/learn` slash command, when invoked with no arguments, emits
    this template to the conversation for the user to fill in and
    re-invoke.

  - The drain hook validates every pending file against the schema +
    blocklist defined in `scripts/lib/staging-schema.sh`. PASS →
    atomic append to `learnings/staging.md` under `flock`, temp file
    removed. FAIL → temp file moved to `learnings/pending/.rejected/`
    with a `# REJECTED: <reason>` header prepended.

  - The read-only `curator` analyst reads a snapshot of
    `learnings/staging.md` plus the distilled `learnings/evidence.md`
    ledger, clusters entries by *theme* (the `target` is a hint, not a
    grouping key), and drafts ranked change proposals. The `/curate`
    conductor walks them past the user one at a time and opens one PR
    per approved proposal; every entry — proposed or not — folds into a
    theme record in `evidence.md` and is copied verbatim into the cold
    `archive.md`.

  How to emit a lesson from a skill
  ---------------------------------

  Emission-site skills follow a fixed recipe so every lesson — no
  matter which skill produced it — lands in `learnings/pending/` in
  the same shape. The recipe has four moves:

  1. Generate a fresh v4 UUID. Use the Bash tool:

         uuidgen | tr 'A-Z' 'a-z'

     The lowercase fold matches the validator's `[0-9a-f]` regex; an
     uppercase UUID fails schema validation.

  2. Capture an ISO-8601 UTC timestamp at the moment of emission:

         date -u +%Y-%m-%dT%H:%M:%SZ

     Use the moment the lesson was identified, not the moment the
     drain hook will process the file.

  3. Resolve the pending directory. Prefer
     `$CLAUDE_PROJECT_DIR/learnings/pending/` when the env var is set;
     otherwise fall back to `<repo-root>/learnings/pending/`. The
     directory exists in checkouts of Flux; on a fresh repo
     `mkdir -p` it first.

  4. Write the file using the Write tool with an atomic rename. The
     filename stem combines a session-uniqueness prefix and the UUID
     so the drain hook's lexicographic glob produces a deterministic
     order, and the rename keeps the drain hook from racing a
     half-written file:

         <pending-dir>/<session-id>-<uuid>.md.tmp   # Write tool target
         mv <…>.md.tmp <…>.md                       # atomic rename

     `<session-id>` is any short token unique within the directory
     (e.g. `head -c 4 /dev/urandom | xxd -p` if a session id isn't
     readily available). The UUID already guarantees uniqueness; the
     prefix exists so a human glancing at `pending/` can tell which
     session a file came from.

  The body of the file is the front-matter block above, with the
  required fields filled in (and any advisory hints the site has). Do
  not invent new fields; keep the documented field order — the validator
  is order-tolerant but human readers diffing entries are not. A minimal
  hand-filed entry is just `uuid`, `timestamp`, and `proposed-text`.
-->
